# decision-review

変更内容と必要な周辺情報を `foundation decide` に渡し、質問ごとの判断確率をレビュー材料として確認する。
結果は確認を助ける材料であり、合否や正しさの証明ではない。
判断モデルの概念は `decision-model-knowledge`、CLI と応答形式は `decide-cli` を参照する。

## 質問セット

質問は `questions.json` にあり、`spec.py` で `foundation decide` 互換の spec にする。

- `doc`: 文書に書かれた更新のたびに変える固定値、既存文との重複を確認する。
- `test`: テストコード内で独自クラスを定義しているかを確認する。
- `fp`: 言語に依存しない関数型設計の観点を確認する。
  `fp-principles` の一部の原則を質問にしたもので、関数型設計全体を網羅しない。
この `fp` 質問セットは新規であり、実測・評価していない。
文書・テストについての過去の実測は、`fp` 質問の有効性を検証していない。
質問は記載された命題そのものについて尋ねる。
命題が当てはまることだけで、常に原則違反だとは限らない。

文書・テストについて「意味のないテストか」は質問に含めない。
過去の実測で、指摘箇所と修正後の状態に差が出なかったためである。

## 実行

1. 対象の種別（`doc`、`test`、`fp`）を選び、差分と判断に必要なファイル本文を入力ファイルにまとめる。
   重複や実装との関係を見る場合は、差分だけでなく比較対象の全文も含める。
2. spec を作る。
   `python3 -I "${HERMES_HOME:-$HOME/.hermes}/foundation/skills/decision-review/spec.py" <doc|test|fp> <input-file> > spec.json`
   インストール先のスキルを絶対パスで呼ぶため、作業ディレクトリがリポジトリ外でも実行できる。
3. Jev / Microsoft-Decision の判断モデルを使う場合は provider を明示して `foundation decide --provider typesafe --dry-run --spec spec.json` または `foundation decide --provider microsoft --dry-run --spec spec.json` で送信先と本文を確認し、同じ `--provider` を付けて実行する。
   省略時の既定値 `openai-codex` は別の provider であり、Jev や Microsoft-Decision ではない。
   新しい CLI や独自の応答変換を追加せず、既存の `foundation decide` の形式を使う。
4. 成功した場合は、標準出力の実際の JSON 応答を確認し、全質問の名前と全確率を表示する。
   CLI は全 provider で provider の生応答をそのまま出力する。
   OpenAI の応答も `answers.<name>` には正規化されない。
   内部呼び出しの `communicate()` で行う OpenAI 応答の正規化と混同せず、CLI の raw response format は `decide-cli` スキルを参照する。
   predicate は `noul`、choice と score は `probabilities` の全値を確認する。
   score は `legend` のラベルと対応させて表示する。
   TypeSafe / Microsoft も各 provider の JSON 構造を確認して各回答の全確率を表示する。
   確率で質問を足切りしたり、低い確率を隠したりしない。
   各確率は命題が真であると判断された度合いであり、コードの正しさや誤りを証明しない。
5. コマンドの非ゼロ終了、API/通信エラー、不正な JSON、または質問の一部でも回答・数値確率が欠けた場合は「未確認」として報告する。
   不足した回答を「該当なし」や低確率として扱わない。
   成功した完全な回答の低い確率と、エラー・部分回答を区別する。

判定結果だけを根拠に commit や push を止めない。

## 関数型原則の確認手段

同じ `fp-principles` を複数の手段で確認する。

- プロジェクトの決定的な機械チェックは、プロジェクト側の hook が担う。
  このスキルは hook を実装・設定・インストールしない。
- 目視で判定できる個別の問いは、このスキルの `fp` 質問セットを判断モデルに渡す。
- 複数モジュールにまたがる設計意図や複雑なトレードオフは、必要な文脈を渡して LLM にレビューさせる。

複雑さに応じて適切な手段を選び、機械チェックの不在を判断モデルの結果で補ったことにしない。
質問セットの結果は、人による確認や必要な LLM レビューの代替ではない。

## 過去の実測

PR #150 で、文書とテストの質問を人が実際に指摘した6箇所と、修正後の状態2件で各1回測定した。
これらは当時の文書・テスト質問だけの実測であり、新規の `fp` 質問を測定・検証した結果ではない。
少数のケースで質問文を調整した値であり、一般的な精度や閾値を示さない。

- 固定値: 指摘箇所 0.88 と 0.90、修正後の README は 0.21。
- 重複: 指摘箇所 0.85、修正後の README は 0.20。
  README の別の指摘箇所でも 0.64〜0.66 が出た。
- 独自クラス: 指摘箇所 0.91〜0.95、修正後のテストは 0.09。
- 意味のないテスト: 質問を2通り試し、指摘箇所と修正後で差が出なかった（0.21〜0.47 と 0.29〜0.35）。
  人は実装を読んで判断していたため、判断モデルには向かないとした。

別の変更で確認するまでは参考値として扱う。
質問を変えた場合は、調整に使っていないケースで再測定する。
