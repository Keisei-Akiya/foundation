# review-hint

過去のレビュー指摘のうち、見て判定できるものを、判断モデル（Jev）で事前に検出する。
結果は「人かエージェントが確認する箇所」の目印であり、合否ではない。
判断の概念は `decision-model-knowledge`、CLI の使い方は `decide-cli` を参照する。

## 観点

観点は `questions.json` にあり、変更の種別ごとに分かれる。

- `doc`（README、ADR などの文書）
  - `hardcoded_version`: リリースのたびに書き換えが要る固定値を書いているか。
  - `duplicate_statement`: 追加した文が、併記したファイルや同じファイルの別の箇所と重複しているか。
- `test`（テストコード）
  - `custom_class`: テスト内で class 文により独自クラスを定義しているか。

「意味のないテストか」は含めない。実測で検出できなかった（下記）。

## 手順

1. 変更の種別（`doc` か `test`）ごとに、入力ファイルを作る。
   先頭に変更差分を置き、続けて、重複や実装との関係を見るのに必要なファイルの全文を、ファイル名の見出し付きで併記する。
   差分だけだと、重複や、実装を写しただけのコードを判定できない。
2. spec を作る。
   `python3 -I skills/review-hint/spec.py <doc|test> <input-file> > spec.json`
3. `foundation decide --dry-run --spec spec.json` で本文を確認し、`foundation decide --spec spec.json` を実行する。
4. 回答の `noul`（命題が真である確率）が 0.8 以上の観点を、確認箇所として報告する。
   該当した観点名と、その入力を読んだ上での所見を併記する。
   0.8 未満でも、問題がないとは言い切らない。

判定だけを根拠に commit や push を止めない。

## 実測（PR #150、1回ずつ）

人が実際に指摘した6箇所と、指摘を直した後の状態2件（すべて偽を期待）で測った。

- 固定値: 指摘箇所 0.88 と 0.90。直した後の README は 0.21。
- 重複: 指摘箇所 0.85。直した後の README は 0.20。
  README の別の指摘箇所でも 0.64〜0.66 が出た。誤検知に近い値なので 0.8 を境にした。
- 独自クラス: 指摘箇所 0.91 から 0.95。直した後のテストは 0.09。
- 意味のないテスト: 質問を2通り試し、指摘箇所と直した後で差が出なかった（0.21〜0.47 と 0.29〜0.35）。
  人は実装を読んで判断していたため、Jev には向かない。人かエージェントのレビューに残す。

件数が少なく、質問文は同じケースを見て調整した。
別の PR で誤検知の量を確認するまで、結果は目安として扱う。
質問を変えたら、同じ手順で再測定する。
