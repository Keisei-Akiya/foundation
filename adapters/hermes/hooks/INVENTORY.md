# ECC → Hermes hooks: 27-registration evidence map

**Scope / method.** ECC's `ecc/hooks/hooks.metadata.json` lists 27 individual registrations (10 PreToolUse, 1 UserPromptSubmit, 1 PreCompact, 2 SessionStart, 2 PostToolUse, 2 PostToolUseFailure, 8 Stop, 1 SessionEnd). This inventory treats metadata entries as the countable registrations; consolidated dispatchers are one registration, with their child checks listed separately below. Evidence combines code/config inspection with the integration tests recorded under “Cross-cutting evidence and caveats” (not live user configuration). “Confirmed” means the stated source contract or the specifically described test behavior was inspected/exercised; it does not imply broader parity. ECC paths are relative to `../ecc`; Hermes source checkout is resolved by the test via `HERMES_AGENT_DIR` or documented default locations; adapter paths are relative to this directory.

**Status meanings:** *Partial* = a scoped adapter/helper exists but does not reproduce ECC behavior or is not connected; *No equivalent* = no equivalent implementation found in inspected adapter/Hermes integration; *Unverified* = runtime behavior or an event/configuration claim was not exercised. Gaps include platform/event mismatch, unavailable API/state, missing opt-in/config, or deliberately narrower semantics. Do not infer parity from a matching filename.

## Cross-cutting evidence and caveats

- The requested test command `uv run --no-project --with pytest --with ruamel.yaml pytest -q tests/test_ecc_integration.py` completed with **7 passed** in this checkout. It imports Hermes' `agent/shell_hooks.py`, tests constructed hook configs/callbacks in an isolated temporary `HERMES_HOME`, and checks that commented `hooks.example.yaml` parses as empty YAML. The callback tests do not load the sample registrations themselves. This verifies only those tested paths, not broad ECC parity or live user configuration.
- Hermes source is resolved from `HERMES_AGENT_DIR` when explicitly set, else from `~/.hermes/hermes-agent` and `hermes-agent` subdirectories of the test file's parent directories. The integration callback tests skip when no valid checkout is found; sample YAML validation remains independent. No user config or real Hermes home is changed.
- Hermes plugin lifecycle capability was inspected in the available source checkout (`hermes_cli/plugins.py`, `tools/skill_usage.py`); `on_skill_lifecycle` delivery to this shell hook/helper is **not confirmed**. `lifecycle.py` is a standalone post-tool shell-hook consumer.
- `stop_lifecycle.py` is an inert helper: its module docstring forbids side effects absent an independently reviewed adapter; it is **not registered** in `hooks.example.yaml`, which explicitly says it is absent. Lifecycle skill helper registration is only an example and event availability is not runtime-verified.
- `hooks.example.yaml` contains commented, individually opt-in entries. Its current contents include pre-tool examples for `preflight_policies.py`, `hookify_runtime.py`, and the `hermes-tool-compat.py config-protection.py` wrapper, plus post-tool observers and a lifecycle helper. README documents the examples and test conditions. These establish sample contents and tested scopes, not that hooks are enabled or runtime behavior outside the named integration checks was exercised.
- `hookify_runtime.py` intentionally fails open on malformed/missing project data. That makes it inappropriate to describe as a fail-closed policy substitute.
- ECC source claims above point to `../ecc/hooks/hooks.metadata.json` for the exact registration IDs/events/descriptions. Behavioral details are based on corresponding implementations under `../ecc/hooks/` and `../ecc/hooks/memory-persistence/`; the named helpers in this adapter are source evidence only, not demonstrated runtime parity.
