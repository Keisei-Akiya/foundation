# ADR 0001: Wiki 検索の未決事項を決める

状態: 持ち主の確認待ち。

## 背景

Issue #17 の wiki 検索では、Jev によるページ選択の入力形式、ドメイン情報の出所、`domains:` が無いページの扱い、1 段目の判定、ページスコアの計算が未決だった。

この ADR は、実際の `~/wiki` からタイトルと要約だけを使い、Jev の小規模な実呼び出しで初期案を選ぶ。

ここで行った呼び出しは設計候補の比較であり、判定精度の評価や閾値調整ではない。

Jev にページ本文は送っていない。

## 決定

### 1. ページ情報を `instructions` に置き、書き直した質問を `input` に置く

ページごとの title と summary を `instructions` に置き、書き直した質問を `input` に渡す。

ページ情報を `input` に置き、質問を各項目の `instructions` に複製する案より、比較対象をページごとに同じ質問で評価しやすい。

同じ書き直した質問は次のとおりである。

「DecisionRAG を使う wiki 検索を設計するとき、Jev に判断させる階層と質問の組み立て方を決めたい。」

この質問を使った。

質問を `input` に置いた実呼び出しでは、DecisionRAG の確率が `none=0.02, low=0.14, high=0.84` になり、Jev 設計ガイドが `none=0.03, low=0.18, high=0.79` になり、TypeSafe AI が `none=0.75, low=0.24, high=0.01` になった。

ページ情報を `input` に置いた実呼び出しでは、DecisionRAG が `none=0.01, low=0.24, high=0.75` になり、Jev 設計ガイドが `none=0.01, low=0.22, high=0.77` になり、TypeSafe AI が `none=0.01, low=0.24, high=0.75` になった。

この小標本では、前者が直接関係する二ページと企業紹介を分け、後者は三ページをほぼ同じ関連度にしたため、質問を `input` に置く案を選ぶ。

`--dry-run` で確認したリクエストでは、どちらの向きでも送信するのは質問、タイトル、要約だけであり、ページ本文は含まれなかった。

### 2. ドメイン名と説明は Wiki の `SCHEMA.md` から読む

スキル側にドメイン一覧を複製せず、Wiki の `SCHEMA.md` の Domain 表を唯一の説明元として読む。

これにより、Wiki の分類定義を変更したときに、スキル側の複製が古くなることを避ける。

質問は次のとおりである。

「AIエージェントを業務に導入するとき、セキュリティ上の統制と導入後のリスク管理を知りたい。」

SCHEMA.md から取得したドメイン説明を使った実呼び出しでは、Yes の確率は `engineering=0.96`、`management=0.62`、`politics=0.11` になった。

この結果は定義を使った一例であり、Jev の応答だけで設定の所有場所を決められるわけではない。

所有場所の決定は、実際の Wiki にすでにある分類定義を正本として扱う保守性を理由とする。

`SCHEMA.md` に説明がないドメインの扱いは、実装時に名前と所属ページ数を使うなど、別途明示する。

### 3. `domains:` が無いページを 2 段目の候補に常に加える

1 段目で選ばれたドメインに属するページに加えて、ドメイン情報が無いページを 2 段目の採点候補に加える。

このページ群は 1 段目で選ばれたドメインへ対応づけられず、除外すると関連する背景情報を見落とすためである。

Wiki の `ipa-daily-2026-09-08` は frontmatter に `domains:` が無いことを確認した。

質問は次のとおりである。

「IPAのAIセキュリティ情報を追うとき、統制設計と実装上の不足を理解するために読むべきページを知りたい。」

同ページのタイトル・要約を使った実呼び出しでは、確率が `none=0.18, low=0.50, high=0.32` になった。

同じ呼び出しで、`engineering` に属する AI エージェントのセキュリティ統制ページは `none=0.02, low=0.07, high=0.91` になった。

未分類ページは直接の答えに限らず背景情報として有用になり得るため、`high` のみで除外せず 2 段目で評価する。

### 4. 1 段目はドメインごとに Yes / No で尋ね、Yes の確率を使う

各ドメインについて独立に「この質問に答えるために、このドメインのページが必要か」を Yes / No で尋ね、`Yes` の確率をそのドメインの確率とする。

「該当なし」の選択肢を設けず、確率の合計を 1 に正規化しない。

質問とドメイン説明は、決定2に記した入力を使った。

`SCHEMA.md` の説明を使った上記の質問で、3 段階方式の `high` 確率は `engineering=0.92`、`management=0.44`、`politics=0.02` だった。

同じドメイン候補を Yes / No で尋ねた実呼び出しでは、`Yes` の確率は `engineering=0.96`、`management=0.62`、`politics=0.11` だった。

小さな比較では Yes / No の方が中程度の関連を低い `high` 値に閉じ込めずに表し、独立したドメイン選択にも直接対応するため、この形式を選ぶ。

閾値と最大ドメイン数は実行時に指定する初期値とし、この小検証から調整しない。

### 5. ページスコアの初期値に `P(low) + P(high)` を使う

ページ採点は `none`、`low`、`high` の3段階を使い、関連スコアを `P(low) + P(high)` とする。

直接の答えに限らず背景として役立つページを拾うという親 spec の優先事項に合わせ、`high` だけでなく `low` の確率も関連ありに含める。

質問を `input` に置いた実呼び出しでは、DecisionRAG は `P(low)=0.14`、`P(high)=0.84` になり、TypeSafe AI は `P(low)=0.24`、`P(high)=0.01` になった。

この例で `high` のみなら TypeSafe AI の値は `0.01` だが、合算値は `0.25` になる。

同じ呼び出しで、`ipa-daily-2026-09-08` は `P(low)=0.50`、`P(high)=0.32` になり、合算値は `0.82` になった。

この合算は初期スコアの選択であり、重み付け、閾値、評価方法の最適化を意味しない。

後続チケットではこの方式を初期値として実装し、実利用ログを得るまでは調整しない。

## 試作をどう扱うか

既存の試作をそのまま継ぎ足さず、後続チケットで決定に沿って検索スクリプトを作り直す。

試作はページ情報を `instructions` に置く点と `SCHEMA.md` を読む点は再利用できる。

一方で、試作は質問を `input` に置き、1 段目とページの両方で `none / low / high` の最上位確率だけを採り、ドメイン無しページを `(none)` ドメインとして扱う。

この ADR は質問を `input` に置く点を維持する一方、1 段目を Yes / No にし、ドメイン無しページを 2 段目へ常に加え、ページスコアを `low + high` に変える。

さらに Issue #116 は全ページを対象にした縦串を先に求め、Issue #117 でドメイン絞り込みを加えるため、試作の2段階構造を段階的に改造するより、新しい決定から小さく作る方が検証しやすい。

参考にした試作の worktree、ブランチ、ファイルは変更も削除もしない。

## 検証の範囲と限界

実機では8件の小規模な Jev 呼び出しを行い、いずれも `jev-1.14.0` が応答した。

送信前に `foundation decide --dry-run` でリクエストを確認し、ページ本文を含めず、Wiki の実データから得たタイトルと要約のみを送った。

ここに記載した確率は各入力に対する応答の抜粋であり、同じ入力を反復した安定性や検索精度を示さない。

ドメイン出所の選択は保守上の判断であり、Jev に二つの実装配置を比較させた結果ではない。

閾値、最大件数、確率の校正、スコア計算の代替案の評価は、この ADR の範囲外とする。
