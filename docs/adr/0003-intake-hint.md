# ADR 0003: intake-hint の spec を実測で確定する

状態: 承認済み。

## 背景

Issue #136 で、人間からエージェントへの入口発話を `foundation decide` で分類する判断層 `intake-hint` を置く。

Issue #137 で、同じ発話セットを使い、フラグ構成を比べる計測ハーネス（`tools/intake-hint/`）を用意した。

この ADR は、#136 の未決事項を、その実測で決めて記録する。

#136 の本文には合成15発話・4問構成の記述が残っている。
現在の spec は5問構成（`proposal`、`reply`、`new_task`、`discuss`、`standing_rule`）である。
本文は更新せず、この ADR を正とする。

## 実測の条件

- 実発話: 60件。非公開の場所に置き、リポジトリには含めない。
- 合成発話: 42件。`tools/intake-hint/synthetic.jsonl`。
- モデル: `jev-1.14.0`。
- 計測は1回ずつである。同じ入力でも応答が揺れ、合成の誤検出は11→12件と動いた。差が1〜2件のものは効果として扱わない。
- 実発話のラベルは1人（アシスタント）が付けた。判断が割れる10件は `ambiguous` とした。

## 決定

### 1. `standing_rule` を採用する

採用は2026-11-21のオーナー決定である。実測は次のとおり。

- 恒久ルールの4件のうち3件で `p ≥ 0.5` になった。残り1件は `p = 0.41` で、低信頼の帯（後述）に入り人間へ戻る。
- 残り56件での誤検出は0件。
- 「`new_task` または `standing_rule`」を指示とみなして数えると、見逃しは4件（4フラグ版）から3件（5フラグ版）になり、誤検出は4件のまま変わらなかった。

差は1件であり、効果があったとは言えない。
採用の根拠は、恒久ルールを `new_task` と区別する要件があることと、誤検出が増えなかったことである。

恒久ルールを含む発話では、`standing_rule` と `new_task` が同時に立つことがある（実発話の2件で両方 `p > 0.8`）。
経路側は `standing_rule` を `new_task` より優先する（#139）。

質問文は変更しない。恒久ルールの標本が4件しかなく、質問文を調整した効果を測れないためである。

### 2. 誤検出より見逃しを重く見る

hint は承認や実行制御に使わないため、誤検出の被害は人間への確認が1回増えることに留まる。

見逃しは、取り違えに後から気づけないことにつながる。
見落とし削減を優先する方針（コストは問題にしない）とも合う。

したがって、迷う側は人間へ戻す（fail closed）。

### 3. 低信頼の閾値は 0.35〜0.65 とする

フラグごとの Yes 確率を `p` とする。

- `p ≥ 0.5` を、そのフラグが立つとみなす。
- `new_task` と `standing_rule` のどちらかが `0.35 ≤ p ≤ 0.65` なら、低信頼として人間へ戻す。

候補ごとの実測（`new_task` と `standing_rule` の両方で、誤りと帯の関係を数えた）は次のとおり。

- 実発話60件、0.35〜0.65: 人間へ戻すのは10件。誤り8件のうち4件を拾う。
- 実発話60件、0.3〜0.7: 人間へ戻すのは15件。拾う誤りは同じ4件。
- 実発話60件、0.4〜0.6: 人間へ戻すのは7件。拾う誤りは3件。
- 合成42件、0.35〜0.65: 人間へ戻すのは6件。誤り14件のうち5件を拾う。

- 合成42件、0.3〜0.7: 人間へ戻すのは8件。拾う誤りは7件。
- 合成42件、0.4〜0.6: 人間へ戻すのは5件。拾う誤りは4件。

0.3〜0.7 は、実発話では戻す件数が5件増えるのに拾う誤りが増えない。合成では2件多く拾う。
0.4〜0.6 は、どちらでも拾う誤りが減る。
実発話を重く見て、0.35〜0.65 を選ぶ。合成の差は、標本の作り方に依存するため決め手にしない。

帯の外にも誤りが残る（実発話で4件、合成で9件）。
モデルが自信を持って外す例は、閾値では拾えない。この限界は受け入れる。

`proposal`、`discuss`、`reply` は、ラベル定義とのずれが大きい（実発話で誤検出20件、20件、不正解26件）。
そのため、これらは経路の判断に使わず、hint として添えるだけにする。見直しは別 issue とする。

### 4. 人間へ戻す経路の形

低信頼、または判断不能（API の失敗、`noul` が返らないなど）のとき、hint は次を返す。

- `route: "human"`
- 理由（`low_confidence` または `undecidable`）
- 各フラグの確率

自動で行動を選ぶことはしない。実装は #139 で行う。

### 5. 評価セットの増やし方

- 合成発話は、リポジトリに置く。構成の比較と回帰の検出に使う。
- 実発話は、非公開の場所に置く。リポジトリには、読み込み手順と形式の検査だけを置く。
- 実発話は、誤検出と見逃しが出たものを優先して追加する。
- ラベルは、2人目が付けた結果と突き合わせる。割れたものは `ambiguous` とし、集計では分けて示す。
- 標本が100件を超えるか、モデルの版が変わったときに、同じ手順で再計測する。

## 結果

spec は5フラグ、閾値は 0.35〜0.65 で確定する。

`src/` を変えるのは #139 以降である。この ADR の時点では、コードの変更はない。

## 戻すときの条件

次のいずれかが起きたら、この決定を見直す。

- 実発話の標本が増え、見逃しと誤検出の比率が大きく変わった。
- モデルの版が変わり、確率の分布が変わった。
- 低信頼の経路に回る件数が、人間の確認の負担として許容できなくなった。
